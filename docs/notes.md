# Рабочие заметки по экспериментам

Ниже не “презентация”, а живой журнал решений.
Фокус: переносимость на Kaggle и стабильность, а не локальный пик.

## Текущее рабочее решение

- активный конфиг: `001_best_solution`
- модель: CatBoost (`iterations=155`, `depth=4`, `l2_leaf_reg=20`, `random_strength=5`, `bagging_temperature=1`)
- порог: `0.58`
- локально (5-fold): `mean_accuracy=0.83501`, `std=0.00858`, `threshold_score=0.84287`
- Kaggle public: `0.82057`
- shift-check: `adversarial_auc=0.681` (умеренный сдвиг, пока принимаем как ограничение датасета)

## Ключевое наблюдение по проекту

На Titanic проще всего “переподогнать” фичи под train и получить красивую локальную метрику.
Почти все решения выглядели хорошо локально и хуже на Kaggle.

Практический вывод: держим в приоритете
1) стабильность по фолдам,  
2) регуляризацию,  
3) аккуратный feature set без агрессивных редких категорий.

## Что проверяли и какие решения приняли

### 0) Бейзлайн

`000_baseline_logreg`
- стартовая точка: логистическая регрессия на 7 исходных колонках датасета
  (`Pclass`, `Sex`, `Age`, `SibSp`, `Parch`, `Fare`, `Embarked`), без feature engineering;
- категориальные — one-hot, числовые — стандартизация; `Fare` сильно скошен, для
  линейной модели логарифмируется (`log1p`); все трансформеры фитятся внутри
  пайплайна по фолдам (без утечки);
- локально (5-fold): `mean_accuracy=0.79799`, `std=0.01403`, `threshold_score=0.81706`, порог `0.58`;
- Kaggle public: `0.77751`;
- shift-check: `adversarial_auc=0.511` (ok) — на сырых фичах сдвига train/test почти нет;
- про `log1p(Fare)`: проверяли логарифмирование скошенного `Fare` — на этом датасете
  эффект в пределах шума (CV ±0.2 п.п., Kaggle ±2 пассажира из 418); приём
  методически верный, оставлен, но измеримого выигрыша не дал;
- роль: нижняя граница, с которой сравниваются feature engineering и бустинги/DL;
- решение: **оставляем как точку отсчёта** (не рабочее решение, а референс).

Сравнение с `001_best_solution` (CatBoost):
- accuracy `0.798 -> 0.835` локально и `0.778 -> 0.821` на Kaggle — feature engineering
  плюс бустинг дают устойчивый прирост ~3.7-4.3 п.п., переносимый на лидерборд;
- стабильность: у бейзлайна `std` выше (`0.014` против `0.009`);
- сдвиг: `adversarial_auc` у бейзлайна ниже (`0.511` против `0.681`) — рост сдвига
  у рабочего решения создают именно инженерные фичи высокой кардинальности
  (ср. с `002` ниже); за прирост точности платим ростом сдвига.

### 1) Валидация и честность пайплайна

- перешли с holdout на 5-fold stratified;
- фит препроцессинга перенесли внутрь каждого фолда (убрали leakage).


### 2) Точечные гипотезы по фичам

`002_ticket_frequency_global`
- гипотеза: считать `TicketFrequency` по train+test, чтобы снизить сдвиг;
- факт: `adversarial_auc` улучшился (`0.681 -> 0.519`), но Kaggle упал до `0.77033`;
- решение: **не брать**.

`003_drop_weak_features`
- гипотеза: удалить `IsAlone`, `Parch`, `HasCabin`;
- факт: устойчивого выигрыша нет, разброс высокий;
- решение: **не брать**.

`004_raw_deck`
- гипотеза: оставить сырую букву каюты;
- факт: добавили редкие категории, переносимости не прибавилось;
- решение: **не брать**.

`018_drop_raw_family_features`
- гипотеза: убрать `Parch`, `SibSp`, `FamilySize`, `IsAlone` как дубли;
- факт: shift стал ниже (`0.644`), но Kaggle хуже (`0.80382` vs `0.80622`);
- решение: **не брать**.

`032_catboost_no_drift_features`
- гипотеза: убрать высоко-кардинальные дрейфящие фичи (`TicketFrequency`, `Surname`,
  `TicketPrefix`), чтобы снизить сдвиг train/test;
- факт: `adversarial_auc` упал (`0.681 -> 0.546`), CV почти не изменился
  (`0.83501 -> 0.82940`, std даже лучше: `0.00858 -> 0.00581`), но Kaggle обвалился
  (`0.82057 -> 0.77511`); порог перепрыгнул `0.58 -> 0.44` — признак сломанной калибровки;
- решение: **не брать**. Второе подтверждение после `002`: снижение adversarial-сдвига
  через удаление Ticket/Surname-фич стабильно роняет Kaggle. Эти фичи несут
  переносимый групповой сигнал; низкий `adversarial_auc` сам по себе не означает
  лучшую переносимость — связь «фича -> таргет» он не измеряет.

### 3) Ограничение сложности модели

Ранняя остановка (`006`, `007`)
- локально выглядело неплохо, Kaggle не подтвердил;
- решение: early stopping сам по себе не лечит переносимость.

Серия по `iterations` (`008`-`013`)
- после ~`150` локальная метрика растет, а Kaggle деградирует;
- решение: не гнаться за большим числом итераций.

Регуляризация (`024`-`031`)
- лучшие признаки: рост `l2_leaf_reg` дал лучший out-of-sample эффект;
- `025_catboost_regularized_l2_20` дал лучший Kaggle (`0.82057`);
- более жесткая регуляризация (`029-031`) уже режет полезный сигнал;
- решение: фиксируем параметры уровня `025` в рабочем конфиге.

### 4) Второй бустинг — LightGBM

`033_lightgbm`
- независимый второй бустинг на полном feature set (как `001`); параметры не тюнились,
  взяты умеренные дефолты (`num_leaves=15`, `n_estimators=200`, `reg_lambda=1.0`);
- факт: лучшая локальная метрика из всех экспериментов (`CV mean=0.85183`), но худший
  перенос — Kaggle `0.77751` (ниже бейзлайна), gap CV->Kaggle ~7.4 п.п., `std=0.01778`;
- вывод: нетюненный LightGBM переобучился под фолды — наглядная иллюстрация главного
  наблюдения проекта (высокая локальная метрика без регуляризации не переносится).
  `001` выигрывает не «как алгоритм», а потому что затюнен и зарегуляризован;
- решение: оставить как задокументированный второй бустинг; для честного сравнения
  алгоритмов LightGBM надо регуляризовать/затюнить наравне с CatBoost.

`034_lightgbm_regularized`
- те же параметры, что у тюненного `001` (n_estimators / lr / depth / L2),
  ключевое изменение `reg_lambda 1 -> 20`;
- факт: Kaggle вырос (`0.77751 -> 0.79425`), gap CV->Kaggle сократился (`7.4 -> 5.1` п.п.),
  `std` ниже (`0.01778 -> 0.01458`); CV почти не упал (`0.85183 -> 0.84511`);
- вывод: регуляризация помогла, но LightGBM всё равно переобучается заметно сильнее
  CatBoost при тех же гиперпараметрах. Причина архитектурная: CatBoost строит
  симметричные (oblivious) деревья + ordered boosting + ordered target statistics —
  встроенная защита от переобучения, которой у leaf-wise LightGBM нет. Зеркалирование
  гиперпараметров не переносит индуктивное смещение алгоритма;
- решение: `001` (CatBoost) остаётся эталоном; LightGBM задокументирован как
  честно сравнённый второй бустинг.

### 5) Deep learning — MLP

`035_mlp`
- PyTorch MLP с entity embeddings для категориальных и нормализацией числовых,
  полный feature set; параметры не тюнились (`hidden=[64,32]`, `dropout=0.35`,
  `epochs=50`);
- факт: `CV mean=0.81481` (между LogReg и бустингами), Kaggle `0.78468`
  (примерно на уровне бейзлайна); `std=0.03696` — самый высокий разброс по фолдам
  в проекте (fold-score гуляет `0.753`-`0.865`), порог `0.63`;
- вывод: на ~700 строках в фолде нетюненная нейросеть нестабильна; параметры взяты
  «на глаз» — следующий шаг подбор гиперпараметров;
- решение: точка отсчёта для тюнинга (`036`).

`036_mlp_tuned`
- те же фичи, гиперпараметры подобраны Optuna (30 trials, family-aware `tune`);
- Optuna выбрал бо́льшую сеть (`hidden=128-64`) с сильной регуляризацией
  (`dropout=0.38`) — высокая ёмкость, зажатая регуляризацией;
- факт: `CV mean=0.83612` (+2.1 п.п. к `035`), `std=0.01618` (вдвое стабильнее),
  Kaggle `0.79665` (+1.2 п.п. к `035`), порог `0.64`;
- вывод: тюнинг перенёсся на лидерборд — около ⅗ прироста CV дошло до Kaggle,
  остальное «съел» лёгкий переобуч CV (gap CV->Kaggle вырос `3.0 -> 3.9` п.п.).
  Тюненный MLP вышел на уровень регуляризованного бустинга `034`, но не побил
  CatBoost — ожидаемо: на 891 строке нейросеть упирается в потолок данных;
- решение: `001` (CatBoost) остаётся эталоном; MLP — задокументированная DL-модель.

`037_mlp_tuned_adamw`
- сменили оптимизатор обучения сети `Adam -> AdamW` (decoupled weight decay)
  и заново затюнили Optuna под него; `optimizer` вынесен в конфиг — `035`/`036`
  воспроизводимы как `adam`, `037` как `adamw`;
- Optuna ушёл к глубокой сети (`hidden=128-64-32`) и очень малому `lr=2e-4`;
- факт: `CV mean=0.82941` (ниже `036`), Kaggle `0.77751` (−1.9 п.п. к `036`,
  на уровне бейзлайна), gap CV->Kaggle вырос до `5.1` п.п.;
- вывод: AdamW методически корректнее, но на крошечной сети и 891 строке разница
  с Adam незначима; перетюнинг нашёл точку с малым lr — сеть, вероятно, недоучилась
  за 52 эпохи. Третье подтверждение (после `log1p` и `032`): на малых данных
  «более продвинутый» приём сам по себе не двигает потолок;
- решение: **не брать**; `036` (Adam) остаётся лучшей MLP-моделью.

- на этом датасете высокая кардинальность (`Ticket`, `Surname`, `Deck`) легко портит переносимость(можно попробовать бакеты);
